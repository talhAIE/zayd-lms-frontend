# STEP Phase 6 — autosave, resume and final results

Implemented locally on `feat/step`, 2026-11-10. This supersedes Phase 5's read-only route boundary. No push, deployment, database/storage operation, production settings change or account/enrollment creation occurred.

## Learner behavior

- Start is enabled on an available topic. It calls the existing STEP start/resume API only on a deliberate click. Duplicate clicks are guarded, and an interrupted Start can be retried against the server's unique student/topic attempt. Existing Resume/View result links read the same attempt.
- Answers save automatically through a STEP-only serial writer. Rapid edits coalesce behind an in-flight request; the latest selection remains visible. Saving, retry, recovered-device answers and revision conflicts have explicit states. No local correctness or marks are calculated.
- Tab-scoped `sessionStorage` journals are keyed by student ID, username, region and attempt ID, with a matching frozen content version. They retain unsaved selections, exact pending request bodies/UUIDs, question position and an unresolved submission body. They contain no question text, keys, tokens or signed audio URLs. Saved answers/content version always come from the API; this introduces no local database or content server.
- Refresh/navigation restores the same question position and pending intent. Failed saves retry with the original request ID/revision before newer choices are sent. Revision conflicts re-read the server and require **Keep my device answers** or **Use saved answers**. The decision re-reads again before rebasing; read failures preserve the draft.
- Submit is disabled until every answer is valid and all saves are confirmed. A current LMS dialog explains that submission is final. The session drains any in-flight save, freezes edits, then sends the exact complete saved set. Results and course/section/topic completion are taken from server responses; returning to those views fetches fresh progress.
- A lost submit reply first triggers a read of that same attempt. If the outcome cannot be confirmed, editing stays locked and **Check submission** is shown. The immutable submit journal survives refresh. A check reads first, then may replay the same request/body; it never silently rebases a final submission onto a different revision. Confirmed submission clears the journal, replaces the player/audio with final total marks and exposes no retake or per-question answer review.
- Account/region/lifetime guards wrap every operation through the existing shared bearer/refresh client. Unmount disposes the writer, aborts requests and prevents queued follow-ups. STEP does not modify NAFS sessions, normal curriculum logic, or shared authentication. Reconnection retries recoverable work; an unload warning protects unconfirmed work. If browser recovery storage fails, a visible warning advises keeping the page open until server confirmation.
